# Four-lens review — 0.1.0 pre-publish (2026-09-03)

> **Status (same day):** every CRITICAL, HIGH, MEDIUM and LOW item below was
> fixed (or, where the item was a documentation/decision gap, documented in
> the README) — see the CHANGELOG for the full list. Validated with 94
> offline tests and 11 integration tests against a real Fabric Warehouse.
> Remaining as future work (0.2.0, tracked in GAP-ANALYSIS): watch,
> line/conditional breakpoints, save/restore, session reset/replay,
> `;`-less statement slicing, nested-EXEC step-into, execution diffs, and
> deeper memory bounding for multi-MB dynamic-SQL sessions.

Independent reviews from four perspectives — data analyst, data engineer,
DBA, developer/QA — consolidated and de-duplicated. Findings confirmed by
more than one reviewer are marked (×2)/(×3). Verdict: **hold the PyPI
release until the CRITICAL and HIGH items are fixed** — the scanner/parser/
state-engine core was approved by all four lenses; the risk concentrates in
the CLI, the CATCH emulation, `;`-less T-SQL in step_into, and session
lifecycle.

## CRITICAL

| # | Finding | Where |
|---|---------|-------|
| C1 (×3) | **CLI exit-code computation crashes without pandas** — `hasattr(list, "__getitem__")` is True, so `df["status"]` raises TypeError on the base install (`pip install tsql-fabric-debugger`); the CLI runs the whole procedure then dies with a traceback | `cli.py:68` |

## HIGH

| # | Finding | Where |
|---|---------|-------|
| H1 | **Post-CATCH skip stops at the first nested TRY** — steps after a nested TRY inside the failed TRY still execute; real T-SQL would skip them | `engine.py` `_run_one` skip loop |
| H2 | **`except Exception` swallows connection failures with no record** — `_ensure_connection` raises outside `_exec_batch`'s try; `_run_one` logs nothing, returns another step's entry and silently finishes | `engine.py` `_run_one` / `_exec_batch` |
| H3 | **`IF x stmt ELSE stmt` without `;` before ELSE** — `skip_stmt` swallows the ELSE into the first branch body; step_into either syntax-errors or silently never runs the ELSE | `parser.py` `skip_stmt`/`consume_branch_body` |
| H4 | **`DECLARE` inside `BEGIN CATCH` breaks emulation** — raw-text execution + full DECLARE prologue → "variable already declared"; the CATCH "fails" masking real behavior | `engine.py` `_emulate_catch` |
| H5 (×2) | **Loose-script path silently persists everything** — `run_script` hardcodes `autocommit=True` while the CLI blurb promises "ROLLBACK by default"; `--commit/--param/--log-level` silently ignored on that path | `runner.py:61`, `cli.py:63-64` |
| H6 | **COMMIT hidden in dynamic SQL escapes detection** — `scan_transaction_controls` only sees word tokens; `EXEC(@sql)` with a COMMIT inside breaks rollback-by-default with no warning | `parser.py` / `engine.py` warning |
| H7 (×2) | **No context manager / non-exception-safe close** — a forgotten `close()` (or an exception mid-debug) leaves an orphan session holding an open transaction and locks on the warehouse | `engine.py` (no `__enter__/__exit__`; `close()` without try/finally) |
| H8 (×2) | **`--param` type inference corrupts numeric-looking strings** — `@code=00123` → int 123 (leading zeros lost), `1e5` → float, `nan/inf` accepted; no way to force a string | `cli.py:_parse_param` |
| H9 (×2) | **`AS BEGIN TRY` body mis-detection** — a procedure without an outer BEGIN...END gets its body truncated to the TRY interior; the CATCH is silently dropped | `parser.py` `procedure_body` |

## MEDIUM (selected, de-duplicated)

- `RETURN` inside the emulated CATCH neither ends the CATCH nor the debug. (`engine.py`)
- Error in `_eval_condition` during step_into bypasses CATCH emulation —
  same block fails differently under step() vs step_into(). (`engine.py`)
- `_run_one` returns the last CATCH entry (SUCCESS) instead of the failing
  step's entry — programmatic consumers read the wrong status. (`engine.py`)
- `ERROR_NUMBER()/LINE()/PROCEDURE()/SEVERITY()` come back NULL in emulated
  CATCH logging; bare `THROW;` errors confusingly. (`parser.py rewrite`)
- `COPY`/`GRANT`/`DBCC` missing from `STMT_START` → IF-condition scan can
  swallow the next statement (`COPY INTO` is a Fabric staple). (`parser.py`)
- SET options (`XACT_ABORT`, `NOCOUNT`) don't persist across parameterized
  batches — non-deterministic divergence. (`engine.py`)
- Child-proc `EXEC` may COMMIT invisibly — no generic warning. (`parser.py`)
- Step numbering invalidated by step_into's mutation of `_steps`;
  `jump_to`/`run_until` silently target different steps. (docs at minimum)
- Ctrl+C untreated: no `cursor.cancel()`, no rollback, desynced env. (`engine.py`)
- `close()` not exception-safe; failed rollback leaves `_conn` set. (`engine.py`)
- `sql()` has no error handling/rollback path and no public `rollback()`. (`engine.py`)
- `autocommit=True` mode gives no "each step persists" warning and even
  suppresses the inner-transaction warning. (`engine.py`)
- `step_timeout` default None = unlimited, contradicting the README's claim;
  no LoginTimeout on the connection string. (`engine.py`, `connection.py`)
- `rows_affected` shows the previous step's value on ERROR/REGISTERED/cond
  entries. (`engine.py:_record`)
- `changed_vars` flattened+truncated at 80 chars — full values unrecoverable
  from CSV; `last_results()` loses the `truncated` flag via pandas. (`engine.py`)
- `--csv` silently ignored without pandas (`except AttributeError: pass`);
  CSV without BOM breaks Excel accents. (`runner.py`, `cli.py`)
- `.sql` files read as strict UTF-8 only — SSMS UTF-16/latin-1 files crash. (3 call sites)
- `sql()` collapses duplicate columns (`dict(zip)`) and loses schema on
  empty results. (`engine.py`)
- `_pending_defaults` re-applied on reconnect after close(), overwriting
  set_var values. (`engine.py`)
- Post-rollback continuation: steps after an emulated CATCH run against
  wiped data and report SUCCESS — needs marking/warning. (`engine.py`)
- Memory growth: `_details` keeps full batches; `_expand_while` O(n²) and
  per-iteration catch registration. (`engine.py`)
- No tests: cli.py (would have caught C1), runner.py, offline engine error
  paths (fake-cursor pattern already exists in test_engine.py).

## LOW / docs (selected)

- README: undocumented constructor params, log/CSV column schema, pandas
  extra, `max_result_rows` cutoff, thread-safety, required warehouse
  permissions (direct DML, not EXECUTE — ownership chaining doesn't apply),
  long-transaction/locking impact, "only debug files you trust".
- `APP=` name on the connection string for DMV visibility.
- `_error_msg` never cleared after CATCH; stale ERROR_MESSAGE() later.
- Multi-message pyodbc errors truncated; raw error not stored.
- `py.typed` shipped with almost no annotations.
- Full log level prints 10 of N rows without saying so; show_vars omits
  table vars from the returned dict.
- run_script fallback `split(";")` cuts inside string literals (use the
  library's own scanner).
- Exit code 1 even when the CATCH handled the error — decide and document.

## Cleared by all four lenses

Scanner correctness (strings/comments/brackets); parameterized re-injection
(no SQL concatenation of values; correct `setinputsizes` for UTF-8);
Entra-only auth with no token leakage; `@@ROWCOUNT` cross-batch semantics;
multi-TRY catch routing + post-END CATCH continuation (non-nested);
batch-scope DECLARE visibility; RETURN detection; table-variable handling;
`BEGIN TRAN` block fix; type round-trip on Fabric (datetime2 ≤6 = Python
precision; unsupported types are Fabric's constraint, not ours);
run_procedure's try/finally; packaging (entry point, extras, lazy imports).
